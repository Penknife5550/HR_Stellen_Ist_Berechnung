## 3. Migrationen anwenden

Falls Drizzle-Migrate konfiguriert ist:
```bash
sudo docker exec -it stellenist-app npx drizzle-kit migrate
```

Sonst manuell pro Datei:
```bash
for m in 0008_deputat_pro_periode 0009_view_pro_tag_range \
         0010_korrektur_layer 0011_view_no_phantom_fill \
         0012_view_no_buffer 0013_aenderungen_filter_zero \
         0014_view_close_korrektur_lueck 0015_deputat_nachtraege; do
  sudo docker exec -i stellenist-db psql -U stellenist -d stellenistberechnung \
    < src/db/migrations/${m}.sql
done
```

Verify:
```sql
-- Sollte 16 Eintraege haben (0000 bis 0015)
SELECT count(*) FROM drizzle.__drizzle_migrations;

-- View muss existieren und Daten liefern
SELECT count(*) FROM v_deputat_monat_tagesgenau;
```

## 6. n8n-Workflows aktualisieren

### #223 v0.7 — Sync (Untis → sync-v2)

1. Bestehenden `#223` als Backup exportieren
2. Datei `docs/n8n/#223_v07 - Stellenist Periodenmodell-Sync (Untis - sync-v2).json`
   in n8n importieren (UI → „⋮ → Import from File")
3. **MSSQL-Credential** zuweisen (`Untis`, ID `HzjHGkJk19cln1C7`)
4. Im Code-Node **„Aufbereiten v0.7"** den `apiKey`-Wert auf den frisch
   generierten Webhook-Key aus Schritt 5 setzen (Suchen-Ersetzen im JS)
5. Test-Run: Workflow inaktiv lassen → „Execute Workflow" → pruefen dass
   beide HTTP-Nodes `success: true` zurueckgeben
6. Alten `#223` deaktivieren, `#223 v0.7` aktivieren

**Hinweis zum n8n-Env-Zugriff**: Self-hosted n8n blockt `$env.X`
standardmaessig. Daher wird der Key direkt im Code-Node hartkodiert.
Wenn ihr `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` setzt, kann der Workflow
auf `$env.STELLENIST_API_KEY` umgestellt werden.

### #224 v0.7 — Notifications

> ⚠️ **`#224` ist veraltet (HMAC kaputt auf n8n ≥ 1.71).** Die Signatur-Nodes
> nutzen `require('crypto')`, das die JS-Sandbox seit n8n 1.71 sperrt
> (*„Module 'crypto' is disallowed"*). Für `hauptdeputat.changed` gibt es den
> korrigierte Einzel-Workflows: **`#225` (hauptdeputat.changed)**,
> **`#226` (verteilung.changed)** und **`#227` (lehrer.created)** — alle mit
> HMAC via Crypto-Node und hartkodiertem Secret. `#224` wird damit nicht mehr
> gebraucht.

1. Datei `docs/n8n/#224_v07 - Stellenist Benachrichtigungen (lehrer + haupt + verteilung).json`
   importieren
2. Outlook OAuth-Credential zuweisen (Platzhalter `DEINE_CREDENTIAL_ID`
   im JSON)
3. Drei Webhook-URLs notieren (n8n zeigt sie nach dem Speichern):
   - `…/webhook/stellenist-lehrer-created`
   - `…/webhook/stellenist-hauptdeputat-changed`
   - `…/webhook/stellenist-verteilung-changed`
4. Workflow aktivieren

#### #225 v0.7 — Hauptdeputat (korrigiert, produktiv)

1. Datei `docs/n8n/#225_v07 - Stellenist Hauptdeputat geaendert
   (Personalabteilung).json` importieren — Outlook-Credential
   (`n8n@fes-minden.de`) ist bereits zugewiesen.
2. **HMAC-Secret ist im Workflow hartkodiert** (Nodes „Signatur vorbereiten" +
   „HMAC SHA256"), NICHT via `$env`. Grund: n8n mit Task-Runner verbietet
   `$env`-Zugriff in Nodes (*„access to env vars denied"*). Das hartkodierte
   Secret muss **identisch** zum Secret des App-Notification-Ziels sein.
   Bei Secret-Rotation **beide Stellen** anfassen (App-UI + diese zwei Nodes).
3. Webhook-URL: `…/webhook/stellenist-hauptdeputat-changed`
4. Workflow aktivieren.

#### #226 v0.7 — Verteilung GES/GYM/BK (korrigiert, produktiv)

Gleicher Aufbau wie `#225`, nur anderes Event: feuert, wenn sich die
Verteilung zwischen den Schulen verschiebt, das Hauptdeputat (Gesamt-WS)
aber **gleich bleibt** (nicht gehaltsrelevant).

1. Datei `docs/n8n/#226_v07 - Stellenist Verteilung geaendert
   (Personalabteilung).json` importieren — Outlook-Credential + hartkodiertes
   Secret bereits gesetzt (identisch zu `#225`).
2. Webhook-URL: `…/webhook/stellenist-verteilung-changed`
3. App-Voraussetzung: Das Event `verteilung.changed` ist im UI
   (`/admin/n8n-webhooks`) abonnierbar (seit dieser Version) — ein
   Notification-Ziel auf die Webhook-URL anlegen, Secret = `#225`-Secret.
4. Workflow aktivieren.

#### #227 v0.7 — Neuer Lehrer (korrigiert, produktiv)

Gleicher Aufbau wie `#225`. Feuert, wenn der Untis-Sync eine neue Lehrkraft
anlegt. Mail: Name / Stammschule-Badge / Untis-ID, Button auf `/mitarbeiter`.

1. Datei `docs/n8n/#227_v07 - Stellenist Neuer Lehrer
   (Personalabteilung).json` importieren — Outlook-Credential + Secret bereits
   gesetzt (identisch zu `#225`).
2. Webhook-URL: `…/webhook/stellenist-lehrer-created`
3. Notification-Ziel in der App anlegen, Event `lehrer.created`,
   Secret = `#225`-Secret.
4. Workflow aktivieren.

### App: Notification-Targets eintragen

Im UI `/admin/n8n-webhooks` (Sektion „Ausgehende Webhooks"):
1. Pro n8n-Webhook-URL einen Target anlegen
2. Beim ersten Target: Events abonnieren — `lehrer.created`,
   `hauptdeputat.changed`, `verteilung.changed`, `sync.completed`,
   `sync.failed`
3. **HMAC-Secret** generieren (in der App) und denselben Wert in n8n
   hinterlegen — **bei `#225` direkt in den zwei Nodes** („Signatur
   vorbereiten" + „HMAC SHA256"), da `$env` vom Task-Runner blockiert wird.
4. „Test"-Button im UI → liefert **HTTP 200, sobald n8n den POST annimmt**
   (Webhook antwortet im Default `onReceived` *vor* dem Workflow!). Ob HMAC
   und Versand wirklich klappen, **nur** in n8n → *Executions* prüfen: läuft
   der Lauf grün bis zum Outlook-Node? Der Test schickt `test.ping` ohne
   `aenderungen` → Mail ist absichtlich leer (prüft nur Strecke + Signatur).

## 9. Periodenmodell-Verhalten

**Was angezeigt wird**:
- Daten enden exakt mit der letzten bekannten `gueltig_bis` aus
  `deputat_pro_periode` (Migration 0012). Beispiel: SY 2025/26 endet
  19.07.2026 → Aug-Dez 2026 sind leer bis SY 2026/27 synct ist.
- Geplante Werte werden nicht verheimlicht: Untis liefert den Jahresplan
  schon im Voraus, daher zeigt z.B. Mai-Juli 2026 Werte (`§ 3 Abs. 1
  FESchVO` — Stellenist basiert auf den geplanten Stunden).

**Periodenmodell-Card** auf Lehrer-Detailseite:
- Echte Wertwechsel werden farblich differenziert:
  - **Rot** = gehaltsrelevant (Gesamt-WS aendert sich) — Badge `GEHALT`
  - **Gelb** = Verteilungswechsel (nur GES/GYM/BK aendert sich) — Badge `VERT.`
- Inline-Edit fuer das tatsaechliche Wirksamkeitsdatum (statt Untis-Montag)
- Plausibilitaetsvalidation: das Datum muss innerhalb der betroffenen
  Periodenspanne liegen, sonst Fehlermeldung

## 10. Rollback-Plan

Falls etwas schiefgeht:

1. App-Container auf vorigen Tag zuruecksetzen:
   ```bash
   sudo docker compose stop app
   sudo docker run --rm -v stellenist_data:/data \
     <previous-image-tag> ...
   ```

2. DB aus Backup wiederherstellen:
   ```bash
   sudo docker exec -i stellenist-db pg_restore -U stellenist -d stellenistberechnung \
     -c -if-exists < /backup/stellenist_pre_v07_*.dump
   ```

3. Migrationen 0008–0012 sind **additiv** (neue Tabellen + Views, alte
   Tabellen unangetastet). Daher reicht im Notfall ein App-Rollback +
   Beibehalten der neuen DB-Objekte. Die `deputat_monatlich`-Tabelle ist
   nach v0.7 leer; ein Rollback der App auf v0.6 wuerde sie aber wieder
   befuellen, sobald der alte Sync laeuft.
